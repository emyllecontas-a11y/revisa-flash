1. SCHEMA DE study_records (RxDB + Supabase)
------------------------------------------------------------
Fonte: src/lib/db.ts (studyRecordSchema, versão 0) + StudyContext.tsx

Colunas:
- id: string (PK, gerado por uid())
- user_id: string (Clerk user_id, ex: "user_abc123")
- date: string (ISO date "YYYY-MM-DD")
- type: string ("teorico" | "pratico")
- discipline: string (nome da disciplina, ex: "Direito Constitucional")
- topic: string (nome do tópico/subtópico, ex: "Direitos Fundamentais")
- duration: number (minutos, inteiro)
- material: string (opcional, apenas tipo "teorico")
- questionsCount: number (opcional, apenas tipo "pratico")
- correctCount: number (opcional, apenas tipo "pratico")
- wrongCount: number (opcional, apenas tipo "pratico")
- source: string (opcional, ex: "manual", "simulado", "lista")
- observations: string (opcional)
- createdAt: string (ISO timestamp)
- updated_at: string (ISO timestamp)
- isDeleted: boolean (default false, soft delete)

Observações:
- A tabela no Supabase usa RPC `salvar_study_records_batch` para upsert em lote (onConflict: id).
- Não há coluna `auto_generated` nem ligação com ocorrências do Plano de Estudos.
- O StudyContext (Agenda) usa `addRecord`/`editRecord`/`deleteRecord` que chamam a RPC diretamente.
- Listener reativo em `db.collections.study_records.$.subscribe()` recarrega automaticamente.

4. study_tasks (Biblioteca) — Ligação com Agenda
------------------------------------------------------------
Fonte: src/types/study-plan.ts + migration

Campos relevantes:
- id: uuid (PK)
- name: string (ex: "Teoria - Direito Constitucional")
- activity_type: ActivityType ('theory'|'questions'|'review'|'cards'|'exam'|'break'|'other')

A ocorrência (study_occurrences) já denormaliza: task_id, task_name, task_color, task_activity_type.
O StudyTask define o "tipo de atividade" que mapeia para a Agenda:
- theory → tipo "teorico" na Agenda
- questions/review/cards/exam → tipo "pratico" na Agenda
- break/other → não gera registro automático (ou "outro")

Mapeamento ACTIVITY_TYPE_ROUTE_MAP (types/study-plan.ts):
- theory: '/aulas'
- questions: '/erros'
- review: '/flashcards'
- cards: '/flashcards'
- exam: '/simulados'
- break: null
- other: null

5. PROPOSTA DE LIGAÇÃO occurrence ↔ record
------------------------------------------------------------

Opção A — Chave estrangeira composta em study_records (RECOMENDADA)
Adicionar colunas em study_records:
- occurrence_source_type: text ('block' | 'extra')
- occurrence_source_id: uuid
- occurrence_date: date
- auto_generated: boolean (default false)

Chave de negócio para "mesma ocorrência": (user_id, occurrence_source_type, occurrence_source_id, occurrence_date)
→ Única por ocorrência do Plano.

Vantagens:
- Permite upsert idempotente: mesmo occurrence gera/atualiza mesmo record.
- Fácil query: "registros automáticos desta ocorrência" = filtro pelas 3 colunas.
- Não quebra registros manuais existentes (auto_generated=false).

Opção B — Tabela de ligação separada (study_occurrence_records)
- Overkill para 1:1; adiciona complexidade de join.

Opção C — Apenas occurrence_id (FK para study_occurrences.id)
- Problema: study_occurrences pode ser recriada (nova versão da série) → id muda.
- A chave composta (source_type, source_id, occurrence_date) é estável.

DECISÃO: **Opção A** (colunas compostas + auto_generated).

6. PROPOSTA DE COLUNA auto_generated
------------------------------------------------------------

**SIM, necessária.** Justificativa:
- Requisito M1: "Não sobrescrever registros manuais".
- Ao marcar ocorrência como 'done', criar record com auto_generated=true.
- Ao desmarcar, remover APENAS records com auto_generated=true para aquela ocorrência.
- Se usuário criou registro manual no mesmo dia/tópico (auto_generated=false), ele permanece intocado.
- Permite UI futura: badge "Automático" vs "Manual", filtros, auditoria.

Tipo: boolean, default false.
Migração: `ALTER TABLE study_records ADD COLUMN auto_generated boolean DEFAULT false;`
RxDB: bump version do schema studyRecordSchema (atual v0 → v1) + migration strategy se necessário.

7. RISCOS IDENTIFICADOS
------------------------------------------------------------
1. **Sobrescrita acidental de registro manual**
   - Mitigação: antes de upsert automático, verificar se existe record manual (auto_generated=false) para mesma (user_id, date, discipline, topic). Se existir, NÃO criar/atualizar automático.

2. **Duplicatas por race condition (offline → online)**
   - Mitigação: upsert por chave composta (user_id, occurrence_source_type, occurrence_source_id, occurrence_date) no service; RxDB primaryKey continua sendo `id` (uuid), mas query de existência usa a composta.

3. **Pausas (ETAPA 7) suprimem ocorrências**
   - studyPlanService já filtra ocorrências em pausa (isDeleted=true ou status suprimido).
   - Regra: ocorrência suprimida NÃO aparece no hub → não pode ser marcada → não gera record. OK.

4. **Overrides de ocorrência (ETAPA 6) alteram start_time/end_time/tema**
   - Ao criar record automático, usar os valores ATUAIS da ocorrência (override_theme, start_time, end_time).
   - Se override posterior mudar duração, recalcular record no próximo toggle.

5. **Migração de schema RxDB (studyRecordSchema v0 → v1)**
   - RxDB requer migration strategy para schema version bump.
   - Campos novos são opcionais (nullable) → compatível com docs existentes.
   - Estratégia: bump version para 1, adicionar migration function que preenche defaults.

6. **Agenda (calendario.tsx) intocada**
   - Regra de ouro: UI da Agenda (visao==="agenda") NÃO muda.
   - Apenas service/studyPlanService cria records; StudyContext continua funcionando igual.
