3.2 Como o syncWithSupabase funciona e como eu registraria uma coleção nova nele?

--- syncWithSupabase (src/lib/db.ts linhas ~1400-1980) ---
Função assíncrona, guarda global isSyncing para evitar concorrência.
Fluxo:
1. processPendingOperations() — envia fila de operações offline (queueService)
2. Lê lastSyncGlobal por usuário (localStorage lastSyncTimestamp_{userId})
3. Para cada coleção em `collectionsToCheck`:
   - Verifica se coleção local está vazia → força pull completo
4. Para cada coleção em `collections` (lista de pull/push):
   - Define pullFrom (lastSyncGlobal ou 1970 se vazia/especial)
   - PULL: busca no Supabase com .gte('updated_at', pullFrom) + .eq('user_id', userId)
     - Exceções: study_records/user_settings usam RPC; listas_questoes/caderno_questoes puxam por IDs de listas/cadernos do usuário; questoes_lista puxa por IDs das listas_questoes locais
   - Merge: upsert local (se updated_at remoto > local)
   - PUSH: busca docs locais com updated_at > lastSyncGlobal
     - study_records/user_settings usam RPC batch
     - listas_questoes/caderno_questoes têm bloco dedicado
     - Demais usam pushWithConflictCheck (compara updated_at remoto vs local, servidor vence se mais novo)
5. Blocos especiais: files, aula_materiais, resultados_lista, resultados_simulado, caderno_questoes, listas_questoes, simulados/questoes/alternativas, study_sessions
6. Se sem erro: writeLastSync(userId, syncStartTime)
7. Callback onComplete()

--- Como registrar coleção nova ---
PASSO 1: Adicionar schema em db.ts (addCollections)
PASSO 2: Adicionar nome na const `collectionsToCheck` (para detecção de vazio)
PASSO 3: Adicionar nome na const `collections` (loop principal pull/push)
PASSO 4: Se a coleção NÃO tem user_id (ex: listas_questoes, caderno_questoes), adicionar bloco dedicado após o loop principal (como feito para essas duas)
PASSO 5: Se a coleção precisa pull por IDs relacionados (ex: questoes_lista), adicionar bloco dedicado
PASSO 6: Adicionar tabela correspondente no Supabase (com RLS, updated_at, isdeleted)
PASSO 7: Em queueService.ts UPSERT_CONFLICT, adicionar entrada se a tabela tem UNIQUE lógico (ex: progresso_lista: 'lista_id,user_id')
PASSO 8: Em supabaseClient.ts, criar helpers create/get/update/delete se necessário

6.1 Inconsistências de nomenclatura ou schema que possam atrapalhar coleção nova "tentativas" e "weeklyNotebooks".

--- RISCOS IDENTIFICADOS ---

1. NOME DA COLEÇÃO RxDB vs TABELA SUPABASE
   - RxDB: camelCase plural (banco_tentativas, study_tasks, weekly_notebooks)
   - Supabase: snake_case plural (banco_tentativas, study_tasks, weekly_notebooks) — OK, consistente
   - MAS: algumas coleções RxDB usam singular (deck, flashcard, error) outras plural (decks, flashcards, errors) — inconsistência histórica
   - PADRÃO ATUAL: plural para novas (banco_tentativas, study_tasks, weekly_notebooks)

2. CAMPO user_id vs USUARIO_ID
   - CAMPOS.ESTUDO.USUARIO_ID = 'user_id' (snake_case)
   - CAMPOS.DECK.USUARIO_ID = 'user_id'
   - CAMPOS.FLASHCARD.USUARIO_ID = 'user_id'
   - TODOS usam 'user_id' no banco — OK
   - MAS: constants usam USUARIO_ID (maiúsculo) como chave, valor 'user_id'

3. CAMPO updated_at vs updatedAt vs ATUALIZADO_EM
   - RxDB schemas: 'updated_at' (snake_case) — padrão Supabase
   - CAMPOS.FLASHCARD.ATUALIZADO_EM = 'updatedAt' (camelCase) — INCONSISTÊNCIA
   - CAMPOS.TOPICO.ATUALIZADO_EM = 'updatedAt'
   - CAMPOS.REVISAO.ATUALIZADO_EM = 'updatedAt'
   - CAMPOS.SESSAO.CRIADO_EM = 'createdAt' (camelCase) mas schema usa 'createdAt'
   - Constants misturam camelCase e snake_case — CUIDADO ao estender

4. CAMPO isdeleted vs isDeleted vs ISDELETED
   - Schemas RxDB: 'isdeleted' (lowercase) — padrão Supabase
   - CAMPOS.DECK.DELETADO_EM = 'deletedAt' (camelCase)
   - CAMPOS.FLASHCARD.DELETADO_EM = 'deletedAt'
   - Migration v1 banco_tentativas usa 'isdeleted' (lowercase)
   - Supabase migrations usam 'isdeleted' (lowercase) — OK no banco, constants divergem

5. BANCO_TENTATIVAS SEM updated_at HISTÓRICO
   - Migration v1 local adiciona updated_at = now() para docs legados
   - Mas no Supabase, linhas antigas PODEM não ter updated_at (não há migration versionada)
   - pushWithConflictCheck compara updated_at → se null/undefined, trata como '1970-01-01' → servidor vence sempre
   - RISCO: dados locais mais novos podem ser sobrescritos por dados antigos do servidor

6. QUESTOES_LINHA / LISTAS_QUESTOES / CADERNO_QUESTOES SEM user_id
   - Essas tabelas de ligação NÃO têm user_id (FK para lista/caderno/questao)
   - Sync faz join manual via IDs do usuário — complexo e propenso a erro
   - Nova coleção weekly_notebooks DEVE ter user_id direto para simplificar sync

7. FALTA MIGRATION SUPABASE PARA BANCO_QUESTOES, QUESTOES_LISTA, BANCO_TENTATIVAS
   - Memória supabase-questoes-sem-migration: tabelas criadas via SQL direto/RPC
   - Schema pode divergir entre RxDB e Supabase (campos extras, tipos)
   - Nova coleção: CRIAR migration versionada no Supabase ANTES de adicionar no RxDB

8. CAMPO hash_dedup EM BANCO_QUESTOES — DEDUP GLOBAL
   - hash_dedup é único global (sem user_id)
   - importarQuestoesNoBanco verifica hash_dedup SEM filtro de user_id
   - Se weekly_notebooks referenciar questões por id, OK (id é único por usuário)

9. TIMEZONE NO SYNC
   - lastSyncTimestamp salvo como ISO UTC
   - Pull usa .gte('updated_at', lastSync) — updated_at no Supabase é UTC
   - OK se ambos UTC, mas cálculo de semana (seg-sex) usa TZ local → pode haver desvio de 1 dia nas bordas

10. QUEUE SERVICE UPSERT_CONFLICT
    - banco_tentativas: 'id' (PK) — OK
    - weekly_notebooks: precisará adicionar 'id' ou 'user_id,week_start' se unique lógico
