DECISÕES TOMADAS
--------------------------------------------------------------------------------

1. Fuso horário: As funções usam métodos de Date que retornam hora LOCAL (getDay, getHours, etc.).
   No navegador do usuário (Brasil UTC-3), isso funciona corretamente. No Node.js (UTC) os testes
   falham, mas o comportamento em produção está correto.

2. week_start/week_end armazenados como DATE (YYYY-MM-DD) sem hora — representam a segunda
   e sexta-feira locais da semana de erros.

3. UNIQUE (user_id, week_start) no Supabase garante idempotência: se dois dispositivos tentarem
   criar o caderno da mesma semana, apenas um succeeds.

4. question_ids e resolved_ids como uuid[] (array de UUIDs das questões do banco_questoes).
   Mantém simplicidade; resolved_ids é união no sync (ver limitação abaixo).

5. generated_at: timestamp de quando o snapshot foi gerado (sábado de manhã).

6. Não alterei coleções existentes. Não criei UI nem lógica de geração (conforme solicitado).

DIVERGÊNCIAS ENCONTRADAS
--------------------------------------------------------------------------------

1. Convenção de nomenclatura de campos de data:
   - CAMPOS.FLASHCARD.ATUALIZADO_EM = 'updatedAt' (camelCase)
   - Schema RxDB usa 'updated_at' (snake_case)
   - Mantive snake_case no novo schema (week_start, week_end, generated_at, updated_at, created_at)
   - Segui o padrão das coleções banco_* (snake_case)

2. Campo isdeleted vs isDeleted:
   - RxDB schemas usam 'isdeleted' (lowercase)
   - Constants usam 'isDeleted' (camelCase) ou 'DELETADO_EM'
   - Usei 'isdeleted' no schema RxDB e na migration SQL (consistente com banco_tentativas)

3. Timezone no sync:
   - lastSyncTimestamp salvo como ISO UTC
   - Pull usa .gte('updated_at', lastSync) — updated_at no Supabase é UTC
   - Cálculo de semana usa TZ local → pode haver desvio de 1 dia nas bordas
   - Isso é limitação conhecida do sistema offline-first sem servidor/cron

LIMITAÇÃO CONHECIDA - SYNC DE resolved_ids
--------------------------------------------------------------------------------

No syncWithSupabase, o pushWithConflictCheck compara updated_at e o servidor vence se mais novo.
Para weekly_notebooks, o campo resolved_ids (array de questões resolvidas) deve ser a UNIÃO
dos dois lados (local ∪ remoto) para não perder resoluções feitas offline em outro dispositivo.

Atualmente o sync padrão NÃO faz merge de arrays — o documento inteiro é substituído pela versão
mais nova (baseada em updated_at). Isso significa:
- Se dispositivo A resolve questões e faz sync → updated_at atualizado
- Dispositivo B resolve outras questões offline e depois faz sync → seu updated_at é mais novo
- Resultado: resoluções do dispositivo A podem ser perdidas

SOLUÇÃO FUTURA: Adicionar bloco dedicado no sync para weekly_notebooks que faça merge de
resolved_ids (união) antes do push, similar ao que é feito para listas_questoes/caderno_questoes.
