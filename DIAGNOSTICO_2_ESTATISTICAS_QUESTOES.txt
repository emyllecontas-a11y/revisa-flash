RESUMO EM 5 LINHAS
================================================================
1) O Banco de Questões já existe: tabela `banco_questoes` no Supabase e coleção `banco_questoes` no RxDB, com id estável (UUID) por questão.
2) Já existe UM REGISTRO POR TENTATIVA: a coleção `banco_tentativas` grava uma linha nova cada vez que você responde uma questão no Banco (acertou/errou, alternativa, tempo, data/hora).
3) Esse histórico é bem incompleto: `banco_tentativas` NÃO tem coluna `updated_at`, e por isso o sync com a nuvem está quebrado — os pushes são simplesmente ignorados e os pulls usam comparação de data inválida.
4) Resolver simulados e listas NÃO gera tentativas: só grava totais agregados por rodada (resultados_simulado / resultados_lista / caderno_resultados), sem linha por questão.
5) A tela Relatório de Desempenho já faz "estatísticas por questão" por cima de `banco_tentativas`, mas ela é enganosa: trata cada erro como um "erro" e não deduplica questões; só mostra acertos por matéria/assunto.

3. HISTÓRICO POR TENTATIVA — QUAL DOS TRÊS CASOS É O REAL
================================================================

Resposta: existem DOIS regimes diferentes convivendo.

REGIME 1 — "UMA LINHA POR VEZ QUE A QUESTÃO FOI RESPONDIDA": SÓ no Banco de Questões.
  Tabela/coleção: banco_tentativas (db.ts:983-1003, bancoTentativaSchema)
  Campos: id, user_id, questao_banco_id, resposta, acertou, tempo_segundos, contexto,
          caderno_resultado_id, created_at
  Como cada resposta gera um id novo (bancoQuestoesService.ts:245), é HISTÓRICO PURO:
  a mesma questão respondida 5 vezes = 5 linhas.
  Quem chama: BancoPlayerInline.tsx:117 e PlayerLivreModal.tsx:100 (via salvarTentativaAvulsa).

REGIME 2 — "SÓ O ÚLTIMO RESULTADO / CONTADORES": Simulados, Listas e Cadernos.
  * progresso_simulado (db.ts:705-723): 1 documento por (simulado, usuária), sobrescrito a cada
    clique. Guarda `respostas` (mapa numero→letra) só da rodada atual.
  * resultados_simulado (db.ts:726-750): 1 linha por RODADA FINALIZADA, com totais e o mapa de
    respostas daquela rodada. É o mais perto de "histórico", mas não permite perguntar
    "quantas vezes a questão 7 foi errada" sem abrir cada rodada e contar na mão.
  * resultados_lista (db.ts:594-616): idem, por rodada de lista.
  * caderno_resultados (db.ts:963-980): idem, por rodada de caderno — e NEM ISSO, porque nada grava.
  * study_records: agregados (questionsCount / correctCount / wrongCount) — um contador por sessão.

REGIME 3 — "SÓ TOTAIS AGREGADOS": study_records (questionsCount, correctCount, wrongCount,
  occurrenceSourceType, autoGenerated) e getEstatisticasBanco (bancoQuestoesService.ts:172-212),
  que conta questões por banca/disciplina/ano/tipo — nada disso é desempenho.

Resumo direto:
- Banco de Questões → caso 1 (linha por tentativa). ✅
- Simulados / Listas / Cadernos → caso 2 (último resultado + mapa da rodada). ⚠️
- study_records → caso 3 (agregados). ⚠️
- "Estatísticas por questão" (quantas vezes respondi, errei, tempo médio por questão) SÓ é possível
  hoje para o que passou pelo Banco de Questões, e mesmo assim de forma incompleta (ver item 5).

5. SINCRONIZAÇÃO — ENTRA NO SYNC DO RXDB COM O SUPABASE?
================================================================

5.1 Como o sync funciona (2 caminhos)

CAMINHO A — fila genérica (src/services/queueService.ts)
- enqueueOperation(type, table, data) grava em pending_operations (local).
- processPendingOperations() (linha 124) faz, por operação:
    create → supabase.from(table).insert(op.data)
    update → supabase.from(table).update({...sem id}).eq('id', id)
    delete → supabase.from(table).delete().eq('id', id)
  Não existe RPC aqui. É insert/update/delete direto na tabela, com o nome da tabela igual ao
  nome da coleção. As úplicas exceções são UPSERT_CONFLICT (linha 22-25) para progresso_simulado
  e progresso_lista.
- Quem chama enqueueOperation('create', 'banco_tentativas', ...) é
  salvarTentativaAvulsa (bancoQuestoesService.ts:257).

CAMINHO B — sync em lote no load (src/lib/db.ts, função de sincronização)
- Pull: para cada nome da lista `collections` (db.ts:1428-1445), faz
    supabase.from(name).select('*').eq('user_id', userIdStr).gte('updated_at', pullFrom)   (linha 1497-1503)
  Exceções que usam RPC:
    * study_records      → rpc('buscar_study_records_usuario', { p_user_id, p_last_sync })   (db.ts:1457)
    * user_settings      → rpc('buscar_user_settings_usuario', { p_user_id, p_last_sync })   (db.ts:1464)
  Exceções com query especial: decks (shared_with), listas_questoes (por lista), files, aula_materiais,
  resultados_lista, resultados_simulado, questoes (simulado), simulados — todos .from(tabela).select.
- Push: monta docsToPush com
    collection.find({ selector: { user_id: userIdStr, updated_at: { $gt: lastSyncGlobal } } })   (db.ts:1523-1525)
  e chama pushWithConflictCheck (db.ts:54-105), que compara `updated_at` remoto vs local (linhas 96-97)
  e só sobe se o local for mais novo. As exceções de push são RPC:
    * study_records → rpc('salvar_study_records_batch', { p_records: docsToPush })   (db.ts:1531)
    * user_settings → rpc('salvar_user_settings_batch', { p_records: docsToPush })   (db.ts:1536)
    * listas_questoes → bloco manual dedicado (db.ts:1541)

5.2 Assinaturas EXATAS de RPC encontradas (grep em todo o src)
- rpc('buscar_study_records_usuario', { p_user_id: userIdStr, p_last_sync: pullFrom })      — db.ts:1457
- rpc('salvar_study_records_batch',   { p_records: docsToPush })                             — db.ts:1531
- rpc('buscar_user_settings_usuario', { p_user_id: userIdStr, p_last_sync: pullFrom })      — db.ts:1464
- rpc('salvar_user_settings_batch',   { p_records: docsToPush })                             — db.ts:1536
Nenhuma RPC para banco_questoes, banco_tentativas, cadernos, caderno_resultados,
resultados_lista ou resultados_simulado. Essas vão pelo caminho genérico (insert/update/delete).

5.3 Situação do `banco_tentativas` — PROBLEMA GRAVE ENCONTRADO
- `banco_tentativas` ESTÁ na lista de verificação de coleções vazias (db.ts:1410) e na lista de
  pull/push do loop (db.ts:1439), com o nome batendo com a tabela do Supabase.
- MAS: o schema `bancoTentativaSchema` (db.ts:983-1003) NÃO TEM a propriedade `updated_at`.
  Só tem `created_at`.
  Consequências, todas confirmadas no código:
   a) PUSH NUNCA SOBE: o seletor local exige `updated_at: { $gt: lastSyncGlobal }` (db.ts:1524).
      Documentos sem `updated_at` não casam com o seletor → docsToPush fica vazio →
      pushWithConflictCheck nunca é chamado para banco_tentativas.
      (O objeto montado em salvarTentativaAvulsa TEM updated_at, mas o RxDB descarta campos que
      não estão no schema — quem manda é o schema.)
   b) PULL COMPARA CAMPOS QUE NÃO EXISTEM: a query pede .gte('updated_at', pullFrom) (db.ts:1503)
      e depois compara doc.updated_at > localTs (linha 1512-1513). Se a tabela remota não tiver
      updated_at, a query pode falhar ou voltar vazia; se voltar, o patch compara undefined.
   c) Além disso, o comentário no próprio db.ts (linhas 1800-1801) já registra um caso IGUAL:
      listas_questoes "não têm updated_at; por isso o pull genérico por user_id + updated_at voltava
      vazio para sempre e a lista abria sem questões". O mesmo bug de raiz.
   d) Enquanto isso, o enqueueOperation('create', 'banco_tentativas', tentativa) do
      salvarTentativaAvulsa MANDARIA o documento (a fila não filtra por updated_at, ela usa
      insert(op.data)), então pela fila a linha até subiria — DESDE QUE a tabela exista no
      Supabase e a coluna user_id aceite o ID do Clerk. Não achei migration para banco_tentativas.
      (ver item 7)

5.4 Situação do `banco_questoes`
- Não está na lista `collections` do sync em lote (db.ts:1428-1445). Só aparece na lista de
  verificação de vazias (db.ts:1410).
- O sync do banco é feito por funções próprias, todas .from('banco_questoes'):
  * pullTodasQuestoesBanco (db.ts:2243-2300) — baixa tudo em lotes de 500, .eq('isdeleted', false),
    .order('created_at' desc), .range(offset, offset+499)
  * pullBancoQuestoesOtimizado (db.ts:2197-2236) — versão antiga paginada
  * pós-importação (bancoQuestoesService.ts:117-158) — upsert em lotes de 200, onConflict: 'id'
  * comentário sob demanda (bancoQuestoesService.ts:268-320) — select('comentario').eq('id', ...)
  Nenhuma RPC. Tudo query direta.

5.5 Resumo do item 5
- RPCs existentes: só study_records e user_settings (4 assinaturas acima).
- banco_questoes: sync próprio por query direta, funciona, sem RPC.
- banco_tentativas: ESTÁ no sync, mas o schema sem updated_at quebra push e pull (bug real, não
  hipótese).
- caderno_resultados, cadernos, pastas_caderno, caderno_questoes: no sync genérico, com updated_at
  presente nos schemas — ok (caderno_questoes, porém, só tem created_at; db.ts:948-959).

  * as chaves são NUMERO da questão dentro do simulado (não o id da questão),
  * não há tempo por questão,
  * não há "acertou" gravado — só a letra escolhida; para saber se acertou é preciso cruzar com
    as alternativas corretas da questão,
  * e cada simulado tem suas próprias questões (ids diferentes), então "a mesma questão" entre
    simulados não é rastreável.
  → Aproveitamento possível, mas trabalhoso e incompleto.
- resultados_lista: idem (mapa respostas {numero: letra} + areas + acertos_por_area).
- progresso_simulado: só a rodada em andamento; sobrescrito. Sem valor histórico.
- caderno_resultados: NADA (nunca foi gravado).
- study_records: tem questionsCount / correctCount / wrongCount por sessão. É total agregado,
  não permite estatística por questão.

8.2 Resposta direta
- Estatística por questão com passado: NÃO existe passado aproveitável de forma automática.
- O histórico "de verdade" (linha por questão) só passa a existir a partir das respostas dadas
  pelo Banco de Questões / Player — e só enquanto o app for atualizado para não perder esses dados
  (item 5.3).
- Respostas de simulados e listas têm um rascunho aproveitável (o mapa de respostas da rodada),
  mas exigiria um trabalho de reconstrução e ainda assim ficaria sem tempo por questão.

9.3 O que passa a ser possível calcular (estatísticas por questão)
Com uma linha por resposta, dá para responder, por questão:
  1. Vezes respondida (total de linhas daquela questao_banco_id)
  2. Vezes errada (linhas com acertou = false)
  3. Vezes certa (acertou = true)
  4. Taxa de acerto (%) = certas / respondidas
  5. Tempo médio por questão (média de tempo_segundos)
  6. Tempo da última tentativa
  7. Última vez que respondeu (máximo created_at)
  8. Primeira vez que respondeu (mínimo created_at)
  9. Sequência atual de acertos (contar linhas seguidas com acertou = true do fim para o começo)
 10. Quantas vezes a questão foi errada e depois acertada (proxy de "aprendeu")
 11. Questões "sanguessuga": ordenadas por (vezes errada) desc
 12. Questões nunca respondidas (banco_questoes sem nenhuma linha em banco_tentativas)
 13. Desempenho por dia/semana (agrupando created_at) — já existe um esboço disso
 14. Desempenho por disciplina/assunto (cruzando com banco_questoes)

9.4 O que seria o "caderno de erros semanal" (PROPOSTA, descrição)
- Semanal = janela de 7 dias sobre created_at das tentativas.
- Pegar as questões com pelo menos 1 linha em banco_tentativas nos últimos 7 dias e
  taxa de acerto abaixo de um limite (ex.: < 70%).
- Criar automaticamente um caderno (cadernos + caderno_questoes) com essas questões, ou
  reaproveitar o caderno já existente da semana.
- Isso é uma leitura/agrupação; hoje o botão "Criar Caderno com Erros" do RelatorioDesempenhoModal
  já faz algo parecido, só que manual e sem recorte semanal.
