(d) Tratamento de erro do queueService quando um create falha
--------------------------------------------
Arquivo: src/services/queueService.ts, função processPendingOperations.
Trecho do catch (linhas ~255-300):

      console.error(`❌ Erro ao processar operação ...`, {...});
      // 409 Conflict em create significa que a linha já existe no servidor.

      const is409 = status === 409 || String(error?.message || '').includes('duplicate key');

        // NÃO remove: marca como falha definitiva (preserva o dado).

Resumo por caso:
  - Chave duplicada (409 / "duplicate key"): operação é DESCARTADA (considera que
    o servidor já tem). [Com a mudança do UPSERT_CONFLICT, um create de
    banco_tentativas vira upsert por id, então nem chega a dar 409.]
  - Chave estrangeira (questão ainda não existe na nuvem): NÃO é 409; conta como
    retry. Tenta até 5 vezes; depois fica MARCADA como failed=true e PRESERVADA
    (não é perdida). Pode ser reativada por retryFailedOperations().
  - RLS (sem permissão): idem — não é 409, vira retry e depois failed=true.
  - Sem internet: a exceção é capturada; a fila também é reprocessada no evento
    "online" (setupQueueListener / handleOnline). Vira retry e depois failed=true.

(e) pushWithConflictCheck (lote com 1 falha) e pull com updated_at ausente
--------------------------------------------
pushWithConflictCheck (src/lib/db.ts:54-135):
  - Primeiro faz SELECT dos ids remotos e monta remoteMap.
  - Para cada doc local: se não existe remoto -> vai pra toUpsert; se o remoto é
    mais novo (remoteTs > localTs) -> aplica remoto localmente e marca skipped;
    senão vai pra toUpsert.
  - No fim faz UM ÃNICO upsert em lote: .upsert(toUpsert, { onConflict: 'id' }).
  => Se ESSE upsert falhar (ex.: 1 registro viola chave estrangeira porque a
     questão ainda não existe na nuvem), o lote INTEIRO daquela coleção falha
     (é tudo-ou-nada naquele ciclo). O erro é capturado no try/catch do loop
     principal (houveErro=true) e será tentado de novo no próximo sync. Não
     perde dado local; apenas atrasa a subida daquele lote.

pull com updated_at ausente (src/lib/db.ts:1508-1516):
  - Para doc que já existe localmente:
        localUpdated = existing.get('updated_at') || '1970-01-01T00:00:00Z';
        if (doc.updated_at > localUpdated) existing.patch(doc);
    Se o doc remoto tiver updated_at ausente/null, a comparação
    (undefined > data) é false -> NÃO atualiza o existente.
  - Para doc que NÃO existe localmente: collection.insert(doc) (insere de todo
    jeito, mesmo sem updated_at).
  - No nosso caso a coluna remota updated_at tem default now(), então vem
    preenchida; mas, por segurança, documentos sem updated_at são inseridos e
    simplesmente não sobrescrevem versões locais.

(G) RISCOS
================================================================

1) O que acontece com os dados locais ao subir a versão do schema (0 -> 1):
   - Nada é apagado. A strategy apenas ADICIONA updated_at e isdeleted a cada
     tentativa antiga, mantendo todos os campos existentes (inclusive contexto
     e caderno_resultado_id). É uma operação de acréscimo, não destrutiva.

2) O que acontece se o código for publicado ANTES do SQL ser executado:
   - O app tenta gravar/enviar isdeleted, mas a coluna ainda não existe na
     tabela remota. Aí o push do sync em lote e/ou o envio pela fila podem
     FALHAR por coluna inexistente. Por isso o SQL DEVE ser rodado PRIMEIRO.
     (No dia a dia, o app continua funcionando local/offline; o que falha é a
     subida ao Supabase até a coluna existir.)

3) O que acontece se um registro reenviado falhar por chave estrangeira
   (a questão pai ainda não existe na nuvem):
   - No push em lote (pushWithConflictCheck), o upsert é tudo-ou-nada por lote:
     se UM registro viola a chave estrangeira, o LOTE inteiro daquela coleção
     falha naquele ciclo e será tentado de novo no próximo sync (não há perda
     de dado local). Assim que a questão pai existir na nuvem, o sync passa.
   - No envio pela fila (um a um), a falha de chave estrangeira conta como
     retry; após 5 tentativas a operação fica marcada como failed=true e
     PRESERVADA (não é descartada), podendo ser reativada depois.

4) Downlevel/segurança do UPSERT: ao registrar banco_tentativas como upsert por
   id na fila, o comportamento de "create" muda de INSERT puro para UPSERT.
   Como id é a chave primária e cada tentativa tem id único, isso é seguro e
   evita o erro de "duplicate key" quando fila e sync tencionam enviar o mesmo
   registro.

5) Coleções protegidas (calendario.tsx e WeeklyGridEditor.tsx): confirmado,
   git diff VAZIO. db.ts: só o bloco de banco_tentativas (ver diff em D).
