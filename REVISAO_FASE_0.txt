## 4. friendService e RLS — Tabela de amizades

**Arquivo:** `src/services/friendService.ts`

### Tabela `friendships` (Supabase):
```ts
interface Friendship {
  id: string;
  requester_id: string;
  addressee_id: string;
  status: 'pending' | 'accepted';
  created_at: string;
  responded_at: string | null;
}
```

### Fluxo:
- Quem convida cria linha com `status: 'pending'`
- Convidado aceita → `status: 'accepted'` + `responded_at`
- Qualquer um pode apagar (recusar, cancelar, desfazer)
- Ao desfazer, trigger no banco apaga compartilhamentos entre as duas

### RLS (Row Level Security) — **não está no código**, mas implícito:
- Política esperada: cada usuário só enxerga linhas onde `requester_id = auth.uid() OR addressee_id = auth.uid()`
- `loadFriendsOverview` já filtra pelo `myId` passado
- A segurança real está no banco (RLS), não no frontend

### Funções exportadas:
- `loadFriendsOverview(myId)` → `FriendsOverview { amigas, recebidos, enviados }`
- `searchPerson(email)` → `PessoaEncontrada | null` (usa `clerkService.findPersonByEmail`)
- `sendInvite(myId, otherId)` → insert em `friendships`
- `acceptInvite(friendshipId)` → update status = 'accepted'
- `removeFriendship(friendshipId)` → delete
- `listAcceptedFriends(myId)` → `PessoaInfo[]` (para botão "Compartilhar")

### clerkService (busca de pessoas):
```ts
// src/services/clerkService.ts

export async function findUsersByIds(ids) { /* RPC buscar_pessoas_conhecidas */ }
```
- RPCs no Supabase: `buscar_pessoa_por_email(p_email)`, `buscar_pessoas_conhecidas(p_ids)`

## 5. Padrão Offline — ErrorContext, StudyContext, RxDB, sync

### RxDB Schema (`src/lib/db.ts`):
- **Database name:** `revisaflash_db_v2` (constante `DB_NAME` em `src/constants/index.ts`)
- **Soft delete:** campo `isDeleted: { type: 'boolean', default: false }` (maioria das collections)
  - **Exceção:** `listas`, `simulados`, `questoes`, `cadernos` usam `isdeleted` (snake_case)
- **IDs:** `uid()` de `@/utils/helpers` (nanoid-like)
- **updated_at:** obrigatório em todos os schemas para sync/conflito

### Sync (`src/lib/db.ts` → `syncWithSupabase`):
- **Chave de sync por usuário:** `lastSyncTimestamp_${userId}` no localStorage
- **Conflict resolution:** compara `updated_at` remoto vs local → vence o mais recente
- **Push com verificação:** `pushWithConflictCheck` faz SELECT remoto antes do UPSERT
- **Queue offline:** `enqueueOperation` (create/update/delete) → processado quando online

### StudyContext (`src/contexts/StudyContext.tsx`):
```tsx
// Carrega do RxDB com filtro isDeleted: false
const result = await db.study_records.find({
  selector: { user_id: userId, isDeleted: { $ne: true } }
}).exec();

// Listener reativo
db.collections.study_records.$.subscribe(() => { debounce(loadData) });

// Add/Edit/Delete → RxDB primeiro → RPC salvar_study_records_batch → queue se falhar
```

### ErrorContext (`src/contexts/ErrorContext.tsx`):
- Mesmo padrão: RxDB + `isDeleted` + sync via `enqueueOperation`
- `addOrIncrementError` evita duplicatas (mesma questão + disciplina)

### Exemplo típico:
```ts
function localDateStr(d: Date): string {
  const y = d.getFullYear();
  const m = String(d.getMonth() + 1).padStart(2, '0');
  const day = String(d.getDate()).padStart(2, '0');
  return `${y}-${m}-${day}`;
}
```

### Uso no Calendário:
- `new Date()` → `getFullYear()`, `getMonth()`, `getDate()` → tudo timezone local
- `toLocaleDateString('pt-BR', ...)` para exibição
- Datas armazenadas como string `YYYY-MM-DD` (ex: `"2026-11-24"`)

### Função centralizada "hoje local":
- **Não existe** — cada componente reimplementa
- Recomendação: criar `src/utils/date.ts` com `getLocalDateKey()`, `getTodayLocal()`, `formatLocalDate()`
