## 1. RESUMO DA HIERARQUIA DE CONTEÚDOS (aba "Conteúdos")

### 1.1 Tabelas/Schemas no Supabase

| Tabela | Colunas-chave | Ligações (FK) |
|--------|--------------|---------------|
| `disciplines` | `id`, `user_id`, `name`, `created_at`, `updated_at` | — |
| `topics` | `id`, `user_id`, `discipline_id`, `name`, `status`, `planned_date`, `order`, `created_at`, `updated_at`, `is_deleted` | `discipline_id → disciplines.id` |
| `subtopicos` | `id`, `user_id`, `topico_id`, `name`, `status`, `order`, `createdAt`, `updated_at`, `isDeleted` | `topico_id → topics.id` |
| `aulas` | `id`, `user_id`, `titulo`, `descricao`, `terabox_url`, `disciplina` (string), `assunto` (string), `subassunto` (string), `assunto_ordem`, `ordem`, `created_at` | Campos textuais (não FK) — `disciplina`, `assunto`, `subassunto` espelham nomes |

> **Observação importante:** `aulas` usa **strings livres** (`disciplina`, `assunto`, `subassunto`) para denormalização, **não chaves estrangeiras**. A hierarquia real navega-se via `disciplines → topics → subtopicos`.

### 1.2 Schemas RxDB (local, `src/lib/db.ts`)

| Coleção | Campos | Ligações |
|---------|--------|----------|
| `disciplines` | `id`, `name`, `user_id`, `createdAt`, `updated_at`, `isDeleted` | — |
| `topics` | `id`, `name`, `discipline_id`, `user_id`, `status`, `planned_date`, `order`, `createdAt`, `updated_at`, `isDeleted` | `discipline_id` |
| `subtopicos` | `id`, `user_id`, `topico_id`, `name`, `status`, `order`, `createdAt`, `updated_at`, `isDeleted` | `topico_id` |
| `aulas` | **Não existe schema RxDB** — acesso direto via `aulaService.getAulasDoUsuario()` (Supabase + cache localStorage) | — |

### 1.3 Serviços de Consulta (Supabase Client)

- `getDisciplines(userId)` — lista disciplinas do usuário
- `getTopics(disciplineId)` — lista tópicos de uma disciplina
- **Não há** `getSubtopicos(topicId)` exposto no `supabaseClient.ts` (existe schema RxDB mas sem wrapper Supabase)
- `getAulasDoUsuario(userId)` — retorna todas as aulas com campos `disciplina`, `assunto`, `subassunto` como strings

### 1.4 Como o app monta a árvore hoje
- Componente "Conteúdos" busca `disciplines` → para cada disciplina busca `topics` → para cada tópico busca `subtopicos` (lado RxDB)
- Aulas são listadas planas via `getAulasDoUsuario()` e agrupadas em memória por `disciplina` → `assunto` → `subassunto` (strings)

### 2.4 O que **FALTA** hoje para fazer a ligação
1. **`study_tasks`** — sem `discipline_id`, `topic_id`, `subtopic_id` (opcionais)
2. **`study_theme_timelines`** — `themes` é `string[]`; precisaria virar `topic_id[]` ou `subtopic_id[]` (ou manter string + adicionar IDs paralelos)
3. **`study_occurrences`** — guarda `theme` como string resolvida; precisaria de `topic_id`/`subtopic_id` para saber "onde" a ocorrência acontece
4. **UI** — `TaskLibrary` e `ThemeTimeline` usam inputs de texto livre; precisam de **Seletor de Conteúdo em Árvore** (Disciplina → Assunto → Subassunto)
5. **Botão "Iniciar atividade"** — navega para rota genérica (`/aulas`, `/erros`, etc.) sem passar `discipline_id`/`topic_id` no estado/URL

## 5. RECOMENDAÇÃO DA ARQUITETA

### **Opção B (Vínculo no Tema/Cronograma) — A MAIS EQUILIBRADA**

**Por que não Opção A:**
- Tarefas como "Teoria 90min", "Questões 60min", "Revisão 30min" são **genéricas por design**. Vinculá-las a um assunto específico quebra a reutilização: o usuário teria que criar "Teoria - Direito Constitucional", "Teoria - Português", "Teoria - Direito Administrativo" — explosão combinatória na biblioteca.
- Migração de tarefas existentes é propensa a erros (match por nome livre).

**Por que não Opção C:**
- Match fuzzy (`theme` string → `topic_id`) é frágil. Nomes de temas na timeline ("Direito Constitucional") podem não bater exatamente com `topics.name` ("Direito Constitucional - Parte 1"). Resultado: `topic_id` nulo em muitas ocorrências, botão "Iniciar" cai no fallback genérico.
- Não resolve a raiz: a **Timeline** é o local semântico correto para dizer "neste mês/semana estudo *este assunto*".

**Por que Opção B vence:**
1. **Separação de responsabilidades correta**: Task = "tipo de atividade + duração"; Timeline = "quais assuntos quando". O motor apenas conecta os dois.
2. **Tarefas continuam reutilizáveis**: Uma "Teoria 90min" serve para qualquer assunto da timeline.
3. **Migração controlada**: `study_theme_timelines` tem poucas linhas (uma por mês/semana). Match `themes[]` → `topics.name` por disciplina do usuário é viável e verificável.
4. **Botão "Iniciar" funciona**: O motor propaga `topic_id` da timeline para a ocorrência. `OccurrenceModal` navega para `/aulas?topic_id=...`.
5. **Registro Automático consistente**: `study_records` recebe `topic_id` real, não string.
6. **Esforço médio, risco médio**: Não mexe em `study_tasks` (tabela mais usada), só em `study_theme_timelines` e downstream.
